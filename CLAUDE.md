# CLAUDE.md — Navagraha

Vedic astrology app: AI Kundli + reports, with an Astrotalk-style astrologer marketplace that is **paused by default** (`FEATURE_MARKETPLACE`). Full-stack TypeScript: React + Vite client, Express + Drizzle + Postgres server, shared Zod schema.

> Read this file before making changes. Its main job is to stop features being **rebuilt** or **broken**. If you add/remove a feature, update the Feature Inventory below in the same change.

## Commands

```bash
npm run dev      # dev server (client + server) on :5000
npm run build    # vite build + esbuild server bundle — MUST pass before commit
npm run check    # tsc typecheck (alias: npx tsc) — MUST pass before commit
npm test         # vitest run — MUST pass before commit
# Browser acceptance for the launch UX fixes and the birth-place field (against a running build; updated for Direction 3): scripts/acceptance/README.md
npm run db:push  # push schema to DB (drizzle-kit)
```

Before every commit: `npx tsc && npm run build && npm test` must all be green. CI (`.github/workflows/main.yml`, every PR) runs typecheck, build, `npm test` and the `*.db.test.ts` suites against a Postgres service.

## Architecture map

- `client/src/pages/*` — one file per page/route. Routes registered in `client/src/App.tsx`.
- `client/src/components/*` — shared UI (shadcn/ui in `components/ui`). **Shell** (`components/shell/`): `AppShell` wraps every consumer route (not `/astrologer/*` or `/admin*`) with the Direction 3 navy `TopNav` (desktop ≥768px: Today, Kundli, Ask, Dasha, Panchang, Reports + account pill) and `TabBar` (mobile: Today, Kundli, Ask, Dasha); the rest of the app is in the account menu (`moreItems`, marketplace pages only when it is on). Every page starts with `PageHeader` (navy header on mobile, title block on desktop) — never draw a page-level header or nav. Dasha opens `/kundli?for=dasha` (choose a chart → `/kundli/:id/dasha`) until a chart can be marked as the user's own. No splash screen. The feature is always called "Ask your Kundli".
- `client/src/lib/*` — `queryClient.ts` (`apiRequest`), `push.ts` (FCM, lazy), `agora.ts` (SDK loader), `analytics.ts`.
- `server/routes.ts` — ALL API routes (one big file). `server/storage.ts` — ALL DB access (the `IStorage` class). `server/index.ts` — bootstrap.
- `server/migrate.ts` — idempotent raw-SQL migrations + seeds; runs on boot. Keep in sync with `shared/schema.ts`.
- `shared/schema.ts` — Drizzle tables + Zod insert schemas + types. Single source of truth for the data model.
- **V3 calculation pipeline (single source of natal truth)** — birth input → `server/astroEngine/birthResolver.ts` (coordinates → IANA zone via `geo-tz/all` or explicit `timezone`; historical offset from the tz database; DST gaps/folds rejected unless `utcOffset` disambiguates; UTC instant) → `server/astroEngine/canonical/compute.ts` (`computeCanonicalChart`: Swiss Ephemeris/`sweph` Moshier mode, **Lahiri**, mean node, whole-sign houses) → `CanonicalChart` (`shared/v3/canonical.ts`, strict versioned Zod schema; malformed charts throw). Every consumer reads it: `getKundli` (returns the legacy `chartData` shape as a pure projection via `canonical/legacy.ts`, with `chartData.canonical` embedded), transits, matching, Panchang, Prashna (`prashna.ts`), and the professional `jyotishEngine.ts`. **Do not add another astronomy path**; the Keplerian `planets.ts`/`core.ts` and `swissChart.ts` were deleted.
- `server/astroEngine/*` — pure Jyotish rule modules over canonical longitudes: vargas D1/D3/D4/D7/D9/D10/D12/D60 (`vedic.ts`), Vimshottari (birth Mahadasha at its true start) + Yogini (`dasha.ts`), dignity/avastha (`dignity.ts`; degree ranges per BPHS ch. 3 — the Moon is exalted only in 0–3° Taurus, Mercury in 0–15° Virgo, each peak included; Mercury's Moolatrikona is 15°–20°, the BPHS convention — and older V3 charts get this on read via `withCurrentDignityRules`; the verses still need checking against a primary BPHS edition), bhava/aspects (`bhava.ts`), Ashtakavarga (`ashtakavarga.ts`), yogas (`yogas.ts`), doshas (`doshas.ts`; Mangal Dosha evaluates the common cancellations — own sign/exaltation, the listed sign exceptions, Jupiter conjunct/aspecting — into `cancelledBy`, and a cancelled dosha is not `present`; older V3 charts get this on read via `withCurrentDoshaRules`), Jaimini karakas + Chara Dasha (marked unverified), functional remedies (`remedies.ts`), partial Shadbala (`canonical/shadbala.ts` — Uchcha/Dig/Naisargika only, **no total Rupas**). Longitudes are read through `lon.ts` (missing body throws, never 0°).
- **Interpretation policy** (PR #99): `shared/v3/ashtakavargaPolicy.ts` (`savReading`) is the only reading of house SAV — ≥36 strong support, 32–35 support, 25–31 neutral (no evidence item), 21–24 strain, ≤20 strong strain — used by the evidence engine, the Kundli SAV table, the report reader, the PDF, the glossary and every AI prompt (`server/interpretationPolicy.ts`: `savHouseLine`, `SAV_PROMPT_HEADING`, `NEECHA_BHANGA_RULE`). Never add a second set of bindu thresholds. A cancelled debilitation is labelled "Debilitated, cancelled (Neecha Bhanga)" (`dignityLabel`), never red. Timeline confidence is High only with ≥2 agreeing reasons. Pro prompts get dignities and labelled SAV (none with an approximate time). `tests/unit/interpretation-consistency.test.ts`.
- **Reasoning foundation** (PR #101, internal, shadow mode — nothing user-facing reads it): `server/astroEngine/reasoning/` — `buildFactIndex` (read-only facts of the CanonicalChart under stable ids such as `dignity:Saturn`, `house.lord:10`, `sav.house:10`, with provenance and reliability from `birthDayStability`/`dashaTimingStable`; an unreliable fact keeps its id but its value is withheld (`withheld: true`, no `value`); with an approximate time the set of ids is the same at every moment of the birth date — a Neecha Bhanga fact exists only beside a stable debilitation, and yogas the birth date can form share the one id `yoga:time-dependent`; `derivedFrom` links a dignity to its sign, a Neecha Bhanga to its dignity and an aspect to its house; running-period ids carry the instant, `dasha.running:mahadasha@<ISO>`; all of it read-only), `RULES` (one id per evidence rule; all `unvalidated` until a validation is documented), evidence dependency metadata (`ruleId`, `factIds`, `dependencyTypes` direct (decides the direction)/derived/gate (applicability or strength only)/role/timing, `role`) recorded at each rule site in `evidence/engine.ts` and kept in a side table (`evidenceMetadata(item)`), so evidence items, API responses and prompts are unchanged; `reasoningInput(chart, asOf)` is the read interface for a future reconciliation layer; with an approximate time it hands on only usable evidence whose facts are all reliable. A new evidence rule must declare its inputs and a registry id. `tests/unit/reasoning-foundation.test.ts`.
- **Planetary findings + contradiction classification** (PR #102, same shadow mode, no route/prompt/UI reads it): `reasoning/planetary.ts` `planetaryReasoning(chart, asOf)` → one `PlanetFinding` per planet (`planetFindings.ts`: FactIndex facts kept apart from classifications — natural nature via the engine's `isNaturalBenefic`, functional role via `functionalRoles` in `remedies.ts` (the remedy logic itself, extracted unchanged; its limits are documented there), lordships, natural/chara karaka roles, reliable yogas, admissible evidence by life area) and `classifyContradictions` (`contradictions.ts`: `shared-dependency` — two counted items resting on one fact, read directly, through a combination or through `derivedFrom`; a gate, role, timing fact or shared planet is not enough — `incompatible-claim` (same house, same fact, nothing else deciding), `opposing-natal-readings`, `natal-vs-timing`, `formation-vs-effectiveness`, `natural-vs-functional`, `needs-validation`, `legitimate-mixed`; open classical questions travel in `validationQuestion`). Only admissible evidence (usable, every fact reliable) and FactIndex values are read, so nothing withheld for an approximate time is reconstructed; lordship-based classifications are `withheld` then. It changes no evidence, weight or verdict. `tests/unit/planet-findings.test.ts`.
- **Period and yoga findings + relationships** (PR #103, same shadow mode): `planetaryReasoning` also returns `periods` (`periodFindings.ts`: one `PeriodFinding` per running Mahadasha/Antardasha — the lord's capacity as the existing `dasha.running-lord` rule reads it (`planetCondition`, no new formula), its natural/functional role, its link to each area (rules/occupies/significator from the FactIndex), the rule's recorded effect there and the natal evidence about the lord; the engine applies one capacity direction to every linked area, so each area's `periodDirection` is marked `source: 'shared-period-lord-capacity'`, `areaSpecific: false`), `yogas` (`yogaFindings.ts`: one `YogaFinding` per detected yoga with a reliable fact — formation from `yogaDefinition`, areas from `yogaAreaMapping`, participants read by `dignityDirection`, dusthana weakening, common, `participantPeriodRunning`; formation, verdict contribution, participant periods and effectiveness are four separate things: `verdictContribution` (and each area's `countsTowardVerdict`) is read from the verdicts' own supporting/conflicting evidence (`domainResolution`), with a reason when a yoga counts nowhere (common-experimental, cancelled, counted-under-another-formation, not-usable, neutral-evidence); `effectiveness.assessed` is always false) and `relationships` (`relationships.ts`: participates, period-lord, natal-vs-activation, yoga-condition, yoga-activation (`participant-period-running`: timing only, never effectiveness), shared-dependency, tension; `legitimate-mixed` vs `unresolved` with the open question, `period-neutral` when the period's capacity is neutral; `relationshipStats` shared vs independent cross-finding pairs). With an approximate time a period the birth date can move is withheld and lordships/houses are never inferred; the whole output is identical at every moment of the birth date. `tests/unit/dasha-yoga-reasoning.test.ts`.
- **Shadow reconciliation** (PR #104, internal only, no route/prompt/UI reads it): `reasoning/reconciliationPolicies.ts` (`POLICIES`: each with existing rule, proposed reading, sources, exceptions, impact and three separate statuses — **technical** (`validated`: implemented and tested / `not-implemented`), **classical** (`validated` only with a verified primary text or qualified expert review — none yet / `provisional` / `unresolved`) and **production** (always `not-approved`; checked at load) — plus a shadow role: `provisional-candidate` (shapes the proposed shadow verdict), `what-if`, `diagnostic`, `flag-only`; no verse/chapter is claimed, secondary commentary is labelled as such; `functionalRoleReview` is a provisional Laghu Parashari reading beside the remedy logic, diagnostic only) and `reasoning/reconciliation.ts` (`reconcileFrom`: per area the production verdict via `resolveDomain` and a proposed one from the same resolver on a shadow list where provisional-candidate policies replace items with neutral copies — originals never mutated, no thresholds copied; approximate charts: policies needing houses/lordships are inapplicable). The only provisional candidate is `own-house-lord-not-malefic-occupant` (the own-house rule governs a malefic occupying the house it rules): technically validated, classically provisional, not approved — it needs primary-text validation or qualified expert review before any activation, and its candidate changes are not validated predictions. Results are marked `shadowOnly: true`, `productionApproved: false`; the module has no activation entry point. Report: `npx tsx scripts/reasoning/shadow-comparison.ts` → `docs/reasoning/pr104-shadow-comparison.json` + `PR104_SHADOW_COMPARISON.md`; matrix: `docs/reasoning/PR104_CLASSICAL_VALIDATION.md`. `tests/unit/reconciliation.test.ts`.
- **User-facing reasoning** (PR #105, `USER_FACING_REASONING_V1`, **default off**; `server/userFacingReasoning.ts` is the only entry point and fails safe to the old behaviour): `reasoning/interpretationContext.ts` (`buildInterpretationContext`: one frozen context from reliable FactIndex facts, the **production** verdicts/confidence and their own supporting/conflicting evidence, and the planetary/period/yoga findings that restate them — never a shadow verdict, reconciliation policy or functional-role classification; formation, verdict contribution, participant periods and effectiveness kept apart; a period's `linkedAreas` (its evidence is shown there) are kept apart from its `areas` (it counts there): a neutral period names the areas it bears on and says it counts in none; evidence/fact ids kept) and `reasoning/explanations.ts` (`buildExplanations` → `ChartExplanations` in `shared/v3/explanations.ts`; `groundingBlock` for AI prompts: no dates, no internal terms, never promises a yoga's result). Examples/performance: `npx tsx scripts/reasoning/user-facing-examples.ts` → `docs/reasoning/PR105_BEFORE_AFTER.md`. `tests/unit/user-facing-reasoning.test.ts`.

WebSocket `chat_message`/`astrologer_reply`/`start_billing`/`call_request`/`call_accepted` are refused and an astrologer connecting is not marked online. Every billing tick re-reads its consultation and stops without charging unless the marketplace is on and the consultation is still `active`; `start_billing` needs an `active` consultation.
  - Boot (`runMigrations`, when off): `closeMarketplaceActivity()` — active consultations → `cancelled` (totals untouched; a later `/end` cannot bill or earn on them), astrologers set offline, a cut-short free first chat restored (`freeChatUsed=false`), live streams ended, pending/confirmed bookings and the waitlist cancelled, affected users notified. Paid Pooja bookings, store orders and **closed consultations with billed minutes but no earning/refund** are only reported: `GET /api/admin/marketplace/open-items`.
  - Client: `useMarketplace()` (`lib/marketplace.ts`, from `/api/config` `marketplaceEnabled`); `App.tsx` wraps marketplace routes so they render `MarketplacePaused`; the shell's account menu, Home, Landing, Wallet and Numerology hide marketplace entry points.

## Conventions

- New DB field → edit `shared/schema.ts` AND add idempotent DDL (`ADD COLUMN IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS`) to `server/migrate.ts`. They must match (`tests/unit/schema-parity.db.test.ts` fails on a Drizzle column the migrations do not create).
- Paid in-app purchases use `storage.debitWallet(userId, cost, desc)` (returns null on insufficient balance). Compute totals server-side; never trust client prices.
- Wallet balances change only through atomic, conditional SQL: `tryDebitBalance` / `creditWallet` (never `getWallet` → compute → `updateWalletBalance`). Razorpay recharges are credited only by `settleRazorpayPayment` (`server/rechargeSettlement.ts`) with a `GatewayPayment` **as Razorpay reports it** (verify fetches it by id, the webhook uses the signed raw-body entity, the reconciler the order's payments): same order, `captured`, INR, exactly `gateway_amount_paise` — anything else becomes status `review` (`GET /api/admin/payments/review`), never credited. Never credit from a browser-supplied amount; partly refunded payments and second payments on a credited order also go to `review`. Coupon dates/active flag are judged at order time, usage limits at settlement. `tests/unit/credit-paths.test.ts` pins every wallet write (no unverified settlement path; `settleExternalRecharge` and `updateWalletBalance` were removed). Pre-deploy forensics: `scripts/forensics/` (read only). The pack bonus is fixed at order time; coupons are re-checked at settlement under a row lock (redemption `staged` → `applied`/`void`, one per transaction); referral rewards need a ≥ ₹100 gateway recharge and stop at `REFERRER_MONTHLY_REWARD_CAP` per inviter. `storage.settleRechargeOrder` claims the pending row once — verify, the webhook (`payment.captured`) and the 15-minute reconciler (`POST /api/admin/payments/reconcile` too) all go through it. **Recharge guard** (trigger `release_a_recharge_guard`, `RECHARGE_GUARD_SQL` in `migrate.ts`): the database refuses a Razorpay recharge order without `gateway_amount_paise`, completing a Razorpay recharge without `settlement_verified_at` (set only by verified settlement), and completed direct Snapmint/LazyPay recharges — so an older build (deploy overlap, rollback) fails closed. Never drop it as part of a rollback. `RECHARGES_PAUSED=true` refuses new recharge orders while settlement continues; payment routes answer 503 until boot migrations finish. Database tests (`tests/unit/*.db.test.ts`) run only with a disposable database: `TEST_DATABASE_URL=<disposable db> npx vitest run --no-file-parallelism tests/unit/*.db.test.ts`. The reconciler's timer only touches recharges from its own run; older pending rows go through the admin endpoint, a dry run unless `?apply=1`. Astrologer earnings are the consultation's billed debits, once per consultation (`astrologer_earnings_consultation_uq`).
- Third-party integrations (Razorpay, Agora, Firebase, OpenAI, Google Maps) must **degrade gracefully** when their env keys are absent — never crash boot.
- Client data fetching: TanStack Query with the URL as `queryKey`; mutations via `apiRequest`. Failures throw `ApiError` (`lib/apiError.ts`: readable `message`, `status`, optional `field`) — branch on `status`, never parse the message; show `field` errors on the form field. Never surface raw response bodies.
- Promotional copy must match what billing does: the free-chat entitlement is `FREE_CHAT_MINUTES` (first chat only), exposed as `freeChatMinutes` in `/api/config`; seeded homepage copy is corrected only by guarded, idempotent UPDATEs (`HOMEPAGE_COPY_FIXES` in `migrate.ts`) that match untouched seed text.
- **Timestamps:** `created_at` columns are `timestamp without time zone`, written by `now()` in the DB session's zone. Compare them in SQL (against `now()` or another stored column), never against a JS `Date` parameter — node-postgres serialises a `Date` in the Node process's zone (#117: the report sweeper and legacy refunds; `tests/unit/report-refund-timezones.db.test.ts`, which CI runs with Node and Postgres in different zones). A legacy report order (no `charged_amount`) refunds its matching debit; with none found, its price, or ₹0 for a free-access account.
- Unknown `/api/*` paths return a JSON 404 (`apiNotFound`, `server/httpGuards.ts`), never the SPA HTML. In production `/api-docs` is admin-only and `/metrics` needs `Authorization: Bearer $METRICS_TOKEN` (404 without one).
- Keep secrets out of logs and responses. Public astrologer endpoints return only the `publicAstrologer()` allow-list (`server/publicAstrologer.ts`) and list verified astrologers only; never spread a full astrologer row into a public response. User and astrologer rows go out only through `server/safeRows.ts` (`selfUser`, `selfAstrologer`, `adminAstrologer`: no password hash ever, admins see the bank account's last 4 digits); admin astrologer edits take only `ADMIN_ASTROLOGER_EDITABLE` fields. There is no endpoint that credits a wallet without a verified gateway payment — do not add one.
- Never invent a figure to fill the UI: astrologer rating/experience/price go through `lib/astrologerDisplay.ts` ("New" / hidden when absent), online dots only via `isAstrologerAvailable`, Matchmaking shows the calculated gunas /36 and the eight-koota table only. `tests/unit/no-fabricated-output.test.ts` greps the client for default ratings, experience, prices, scores and audience claims.
- **Design system: Direction 3 — Contemporary Vedic** (approved). Spec: `docs/design/direction-3/SPEC.md`; approved mockups `docs/design/direction-3/mockups/*.html` (do not edit) rendered to `reference/*.png` by `scripts/design/render-reference.mjs`; `scripts/design/compare.mjs` puts the running app beside them (local DB only). Tokens live in `client/src/index.css` (`--ground`, `--surface`, `--ink`, `--amber`, `--amber-text`, … as Tailwind `bg-ink`, `text-amber-text`, `border-line`; type scale `text-caption/lead/card-title/subhead/heading/section/title/hero`; radii `rounded-chip/sm/md/lg/answer/sheet`). ## Known caveats (intentional, not bugs to "fix" blindly)

- Store/report/pooja/gift checkout is wallet-based (no direct per-item gateway yet).
- Live chat uses polling; Agora handles real-time A/V. Stream viewer counts are approximate.
- Natal charts, Panchang and Prashna use the place's historical time zone and real (Swiss) sunrise. With an approximate birth time, Lagna/houses and any dasha period that could differ across the birth date are excluded and disclosed.
- Sade Sati (and every transit house from the Moon) is **undetermined** when the Moon sign is not stable across the birth date (`sadeSati.determined=false`, `moonSignCertain=false`); the guard then refuses any Sade Sati claim either way. With an approximate time the guard also refuses Mangal Dosha claims (it is house-based).
- Chara Dasha is lineage-dependent and marked unverified in the canonical chart; consumer evidence/timeline use Vimshottari only.
- Shadbala is partial (Uchcha/Dig/Naisargika); never present a total.
